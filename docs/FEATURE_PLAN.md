# FEATURE_PLAN · 功能规划与版本路线图

> 本文档规划 SiemensInstallHelper（后续大版本将整合为「西门子百宝箱」）的功能演进路线。
> 目标读者：项目维护者、协作者、对项目方向感兴趣的同学。
> 版本命名遵循 README 的 `V(大版本).(功能版本).(修复版本)` 规则。

---

## 1. 项目定位与愿景

**一句话定位**：面向 TIA Portal / STEP 7 / WinCC 等西门子工业软件的「安装、环境、排障辅助百宝箱」——让不熟悉底层原理的小白，也能像老手一样装得上、查得清、修得对。

**愿景**：
- 不只管「安装」这一件事，而是覆盖 **安装前体检 → 安装中护航 → 安装后维护 → 使用中排障 → 学习中参考** 的全过程；
- 所有功能保持「辅助诊断」边界：只读日志与系统信息、只做白名单式处理、所有改动先备份可回滚；
- 知识库与社区共建：官方维护 + 社区贡献 + AI 初审 + 协作者实测，持续迭代。

## 4. 版本详细规划

### 4.0 v1.1 发布范围调整（提前合入项）

为使 v1.1 发布时开箱即用，从后续版本**提前合入**以下低成本、复用已有逻辑的功能：

| 提前项 | 原规划 | 说明 |
|---|---|---|
| 基础信息一键复制 | v1.4 | 复用 `collect_error_context`，一键复制 Issue 基础信息片段 |
| 环境快照脱敏导出 | v1.2 | 复用 `export_report`，增加脱敏与环境快照 |
| 精简版安装前体检 | v1.2 | 整合已有检查 + 磁盘/路径检查，输出风险清单 |
| 知识库案例扩充 | 持续 | 内测反馈报错并入大白话规则表 |
| 反馈收集入口 | v1.4 | 求助页/报告增加「方案是否有用」反馈复制 |

> 未提前项（卸载清理、运行日志解析、多版本管理等）维持原版本规划。

### 4.1 v1.2「环境体检」— 安装前系统预检

**目标**：在启动 TIA 安装之前，一键扫描本机环境，提前发现会导致安装失败的风险项，从源头减少失败。

> 📌 精简版（已有检查整合 + 磁盘/路径检查）已提前至 v1.1；本版本实现完整版与进阶项（补丁检测、旧版残留检测等）。

**扫描项目**：
- 安装路径检测：是否包含中文、空格、特殊符号（提醒推荐路径，如 `D:\TIA_Portal\V20`）；
- .NET Framework 状态：是否启用、版本是否满足；
- 杀毒软件 / Defender 实时保护状态提示；
- 磁盘剩余空间检查（按目标版本给出参考阈值）；
- 系统补丁缺失检测；
- 旧版 TIA 注册表残留检测。

**交互**：
- 输出风险清单，每条附带 💡 知识库小提示；
- 高危项标橙黄色警告，给出解决步骤；
- 一键生成「环境快照」报告（脱敏），可与日志打包一起提交 Issue。

**验收标准**：预检结果可与后续安装结果对照；风险项全部可追溯至知识库条目。

---

### 4.2 v1.3「维护助手」— 安装后环境维护

**目标**：解决 TIA 已经安装完成后遇到的高频问题，这是新手第二大痛点。

**功能清单**：
1. **卸载残留清理助手**
   - 安全扫描 TIA / WinCC 卸载后遗留的注册表、缓存、临时文件；
   - ⚠️ 不自动删除：列出清单，**用户手动勾选确认后**才清理；区分「安全可清理项 / 谨慎操作项」；
   - 清理前自动备份，可回滚。
2. **TIA 运行日志解析**
   - 解析打开工程、编译、仿真时的运行/崩溃/闪退日志；
   - 自动提取报错并匹配知识库，给出排查方案。
3. **多版本管理**
   - 检测本机已安装的 TIA 多版本（V16~V21），查看路径与 Update 补丁；
   - 提示多版本共存常见冲突。
4. **系统依赖修复向导**
   - .NET、VC++ 运行库、DLL 缺失、权限问题检测；
   - 给出修复步骤与官方链接，不静默安装。

**验收标准**：所有清理操作必须用户确认；所有修复建议附知识库依据。

---

### 4.3 v2.0「西门子百宝箱」— 大版本整合（重磅）

**目标**：从「安装助手」升级为「百宝箱」，统一入口 + 模块化框架，为后续所有模块铺路。

**核心能力（本版本定义）**：
| 模块 | 说明 |
|---|---|
| 新手引导 | 首次启动向导，一步步带小白完成环境体检 → 安装 → 监控 |
| 日志哨兵（含授权修复） | 后台盯日志，发现异常立即提示；授权服务异常时自动修复（先备份） |
| 代码检查 | 对工程相关文件做合规/健康检查（只读） |
| 组件校验 | 校验 .NET / VC++ / 关键组件完整性 |
| 错误大白话 | 所有报错统一「原文 + 大白话 + 操作步骤」展示（延续 v1.0 规范） |
| 卡住预警弹窗指引 | 日志长时间无更新时预警，附排查指引 |

**框架要求**：
- 模块化架构：主程序保持轻量，功能以独立模块组织；
- 知识库、日志、小贴士等基础设施与业务逻辑解耦；
- 为插件系统预留接口（远期）。

---

### 4.4 v2.1「工程辅助（只读）」

**目标**：辅助查看工程、解析编译报错，**不修改 PLC 工程文件**。

**功能清单**：
- 工程信息快速预览：读取 TIA 导出的工程报表，统计 IO 数量、FB 块清单、报警数量；
- 编译错误批量解析：把编译报错翻译成中文，匹配知识库；
- 工程文件健康预检：检查工程碎片、备份完整性，提醒及时备份；
- 仿真环境状态查看：仿真服务是否正常、端口占用排查。

**约束**：只读，不直接修改工程源文件；如需 Openness 高级能力，走远期插件方案（用户自备合法授权）。

---

### 4.5 v2.2「学习与文档辅助」

**目标**：面向学生与初学者，降低学习门槛。

**功能清单**：
- 官方文档检索助手：本地离线索引西门子公开手册，快速检索报错关键词；
- 知识点小贴士扩展（基于 tips 体系，覆盖更多工控知识点、常见坑）；
- 工程规范检查：命名规范、注释提醒（规则可自定义，仅提示不强制）。

---

### 4.6 远期：插件系统

- 主程序轻量化，高级功能以插件按需加载；
- 候选插件：Openness 插件（可选，用户自备合法 TIA 授权）、批量日志分析插件、排障报告导出插件（HTML/Markdown）；
- 不装插件的用户完全不受影响。

## 5. 贯穿性基础设施

### 5.1 知识库体系

三库架构（文件结构统一，程序读取逻辑一致）：

| 文件 | 性质 | 说明 |
|---|---|---|
| `error_db.json` | 官方内置，只读 | 经过验证的报错方案，随版本发布 |
| `error_db_candidate.json` | 实验候选库 | 默认不加载，高阶用户手动开启，内容「仅文档推演 / 少量样本验证」 |
| `user_error_db.json` | 用户本地自定义 | 图形界面增删改，仅本地生效，检索优先级高于官方库 |

**条目 JSON 结构**（与社区评审 NPC 约定一致）：
```json
{
  "id": 1,
  "match_keywords": ["Error 1722", "MSI安装包失败"],
  "title": "MSI组件安装失败 Error 1722",
  "explain": "通俗解释，小白友好",
  "solution": ["步骤1", "步骤2"],
  "related_tip_id": 3,
  "reference": "参考来源（官方文档/日志样本编号）"
}
```

**分类扩展**（随模块增加）：
- `setup`：安装阶段报错（现有）
- `runtime`：TIA 运行/闪退/启动报错（v1.3 起）
- `compile`：工程编译报错（v2.1 起）
- `simulation`：仿真相关故障（v2.1 起）
- `uninstall`：卸载残留问题（v1.3 起）

### 5.2 小贴士体系

双文件架构：
- `tips.json`：官方内置，只读；
- `user_tips.json`：用户自定义，图形界面管理（新增/编辑/删除/恢复默认），不碰源码。

高阶能力（需开启高阶模式）：一键导出用户自定义小贴士 → 生成 PR 贡献素材（JSON 片段 + 说明文档），贡献者后续自学 Git 后即可提交。

### 5.3 社区贡献与评审体系

> v1.1 先行：软件内「这条方案是否有效」反馈收集入口（轻量版，复制模板走微信/邮箱渠道）；完整 Issue/MR 评审链路随 v1.4 落地。

**双仓并行（不分主次）**：
- **CNB（cnb.cool）**：国内主阵地，内置 NPC、云开发环境、CI 流水线、制品托管；国内用户提交 Issue / 合并请求（MR）。
- **GitHub**：海外主阵地，海外用户提交 Issue / PR；代码双向同步。

**评审链路**：
1. 用户提交 MR/PR → CI 流水线（`.cnb.yml` / GitHub Actions）做 JSON 语法、ID 唯一性等硬性校验；
2. 评论区 @知识库评审NPC → 做合规扫描、字段完整性、关键词-日志匹配、技术常识筛查等 AI 初审，输出结构化报告并打标签；
3. 维护者 + 可信高阶协作者（CNB「助手」角色，可评审不可合并）认领，在**合法 TIA 环境**复现验证；
4. V20 可复现 → 验证通过并入正式库；其他版本或无法复现 → 转入实验候选库，收集软件内「这条方案是否有效」反馈，积累后转正；
5. 主分支开启保护，禁止直接 push，合并权保留在维护者。

**标签体系**：`ai-passed` / `ai-warning` / `ai-rejected` / `needs-community-test` / `experimental-kb` / `verified` / `tip-contribution` / `kb-contribution` / `log-sample` / `known-error` / `new-error-case` / `content-warning` 等。

**模板目录**（随仓库落地）：
- GitHub：`.github/ISSUE_TEMPLATE/`、`.github/PULL_REQUEST_TEMPLATE/`
- CNB：`.cnb/ISSUE_TEMPLATE/`、`.cnb/PULL_REQUEST_TEMPLATE/`、`.cnb.yml`

### 5.4 日志规范

沿用既定规范（详见项目日志需求文档）：
- JSON Lines（jsonl）格式，一行一条，UTF-8；
- 字段固定：`timestamp`（ISO8601 带时区）、`level`、`module`、`event`、`msg`、`metadata`；
- 百宝箱自身日志与 TIA 原始日志分文件存储；文件首行注释说明；
- 滚动策略：单文件 ≤ 10MB，最多保留 5 份历史；
- 一键打包导出（App 日志 + TIA 原始日志 + 环境信息），供提交 Issue / 离线分析。

### 5.5 发布规范

- **CNB**：同步源码、版本 Tag、说明文档；**不直接上传 EXE**（平台限制）。
- **GitHub**：Release 发布页托管 EXE 安装包；CNB Release 描述中标注 EXE 下载跳转 GitHub。
- **更新日志**：对外 Release 概要简明适度（拒绝「修复了一些已知问题」式一句话）；仓库内 `CHANGELOG.md` 记录完整技术改动与彩蛋备注。

## 6. 软件架构规划

```
SiemensInstallHelper（主程序 / GUI）
├── 模块层（按功能版本逐步加入）
│   ├── 环境体检（v1.2）
│   ├── 安装护航（v1.1 / v2.0 强化）
│   ├── 维护助手（v1.3）
│   ├── 工程辅助·只读（v2.1）
│   └── 学习辅助（v2.2）
├── 基础设施层（贯穿）
│   ├── 日志模块（jsonl + 滚动 + 打包导出）
│   ├── 知识库引擎（三库 + 分类 + 检索 + 反馈）
│   ├── 小贴士引擎（默认 + 用户自定义）
│   └── 贡献素材生成（基础信息片段 / PR 素材 / 本地预检报告）
└── 插件接口（远期）
```

**原则**：新增故障类型只需扩充 JSON，不大量改动主程序；每个模块独立迭代、独立验证。

---

## 7. 红线与合规（所有模块通用）

1. 不逆向 TIA 安装程序二进制，不注入、不劫持、不修改 TIA 本体；
2. 不处理任何授权、密钥、序列号、破解相关能力；不索取、不分发相关资源；
3. 任何修改类操作（清理、修复）必须先备份、后执行，且由用户确认；
4. 读取工程信息优先用官方导出报表，不直接改写工程源文件；
5. 社区贡献内容禁止包含破解/激活相关内容，发现即拒；
6. 软件不上传任何数据，所有提交操作由用户手动完成。

## 8. 风险与依赖

| 风险 / 依赖 | 应对 |
|---|---|
| 缺少多版本 TIA 环境，无法逐一复现验证 | 候选知识库 + 社区协作者分担 + 用户「方案是否有效」反馈转正机制 |
| 新版本 TIA 迭代（约 12~16 个月一个大版本） | 依托公开 Release Notes / 兼容性文档提前预适配，新版条目先入候选库，正式发布后实测转正 |
| 与西门子沟通 | 只对接公开技术资料与官方提供的能力；若官方提供测试介质，严格遵守其使用约束，不二次分发 |
| 社区贡献质量参差 | NPC AI 初审 + 人工复核 + 候选库机制兜底 |
| 平台能力差异（CNB/GitHub） | 双仓各自适配（MR/PR、`.cnb.yml`/Actions），评审规则统一 |

## 10. 迭代节奏建议

- **每 12 个月**一轮大版本适配（跟随 TIA 大版本节奏）；
- 平时持续接收社区日志样本、报错方案，增量迭代知识库；
- 每个功能版本发布前，先内测（沿用 v1.1 内测模式），收集反馈后转正式版。
